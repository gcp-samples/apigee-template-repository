Why does Client Registration have to be done first?
OAuth 2.1 strictly requires the Authorization Server (Apigee) to know client identity, redirect URIs, and allowed scopes before any authorization code or token can be issued.
  • Option A: Dynamic Client Registration (DCR - RFC 7591) (Recommended): Automatically registers this single-page app in Apigee with a single click.
  • Option B: Client Identity Metadata Document (CIMD): In modern OAuth 2.1 / MCP, the client ID is a URL hosting client metadata. Apigee fetches this document on-demand without prior registration.
  • Option C: Existing App Credentials: If you already configured a Developer App in the Apigee console, enter its Client ID here.

Why User Flows & PKCE Authentication?
Apigee acts as the Identity Provider (IdP), maintaining user accounts as Apigee Developer entities.
  • User Flows: Before authenticating, create an end-user account (/register-user) and optionally set up MFA (/mfa-setup).
  • Authorization Code with PKCE (RFC 7636): OAuth 2.1 prohibits client secrets in single-page apps. A cryptographic code_verifier and SHA-256 challenge (PKCE) protect the authorization code from interception.

Why Endpoint Testing & Token Verification?
This tab tests backend APIs and MCP tools protected by the auth-oauth-verify feature template.
  • Bearer Token: Verifies that valid access tokens with appropriate scopes allow authorized access (200 OK).
  • None (401 Check): Verifies that unauthenticated requests are properly rejected by Apigee with 401 Unauthorized.
  • API Key: Verifies fallback API Key authentication if enabled.
